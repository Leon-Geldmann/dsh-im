## 三、核心数据模型与不可破坏的约定

### 1. 服务器绑定 DSH

第一版采用“一个 DSH 实例＋一个专属 Bot＋一个指定 Guild”。

持久保存绑定身份，校验 Guild ID、Bot 身份和 DSH 实例身份。启动时发现身份冲突应明确报错，不能自动接到另一个实例。

允许配置我的 Discord 用户 ID 白名单。私有服务器也必须检查实际操作者，不能把“能看到频道”视为“可以执行 DSH 指令”。

进入下载附件、创建会话或调用 DSH 之前完成权限与路由检查。

### 2. Category 绑定项目

建立以下映射，字段名称可以按现有架构调整：

- Guild → DSH 实例。
- Category ID → 项目 ID、DSH Workspace／分组标识、项目工作目录。
- Channel ID → Session ID、项目 ID、生命周期状态。

所有 Discord ID 以字符串保存，不能转成可能丢精度的 JavaScript Number。名称仅用于显示，不作为绑定主键，不直接拼成文件系统路径。

先核实实际 DSH 的 Workspace、会话分组和 cwd 语义：

- 当前 dsh-im 集成已有 workspace.list、workspace.create({path}) 和按 workspaceId 创建会话的逻辑，可优先复用。
- 默认按“每个项目明确关联一个工作目录”实现。
- 如果 DSH 存在独立于目录的原生会话文件夹接口，合理使用它，并保持分组与执行目录的区别。
- 不猜测不存在的 API，不直接编辑 DSH 内部数据库／会话文件来伪造支持。
- 新建项目涉及创建目录时，限定在配置允许的项目根目录；绑定已有目录时校验其真实性。

同项目会话可以共享项目文件和明确的项目规则，但各频道的对话上下文保持独立。不得把同一 Category 下所有频道聊天自动拼入每次模型请求。

### 3. 一个频道固定对应一个 Session

这是本项目最重要的约定：

一个受管文字频道在其生命周期内只对应一个固定的 DSH Session ID。

具体要求：

- `/new` 或“新建会话”必须新建文字频道和新 Session，默认放到当前项目分组。
- 不能沿用“在原频道悄悄替换 active Session”的行为。
- 打开已有 Session 时，复用它在本服务器已有的有效频道；没有入口时创建频道，或绑定一个尚未使用的空频道。
- 一个 Session 在该服务器最多有一个有效会话频道。
- 已映射项目中新建的普通文字频道，可以在首条授权用户消息到达时建立 Session；处理并发，避免创建重复会话。
- 重命名、重连、插件重启、模型切换不改变绑定。
- 已绑定 Session 暂时找不到或查询失败时，保留映射并显示错误，不能自动创建替代 Session。
- 对现有共享逻辑中“失效 Session 自动补建”的行为，在此模式下作适当隔离。
- 深度归档后重新打开可以创建新的 Discord 频道，但必须恢复原 Session，并保留历史映射记录。

### 4. 生命周期操作

明确实现并记录以下行为：

- 频道改名：保留 Session 和工作目录。
- Category 改名：保留项目标识和工作目录。
- 频道被拖入另一个项目分组：检测并标记归属冲突；在处理前不向错误目录提交新任务。
- 如果 DSH 支持保留 Session ID 的原生分组／工作区迁移，通过明确的迁移操作使用。
- 如果不支持迁移，提供还原频道分组或在目标项目另建会话的清楚选项，不能伪装迁移成功。
- 任务运行中不自动改变其工作目录。
- 删除 Discord 频道／Category 不删除 DSH 历史或项目文件。
- 编辑、删除旧 Discord 消息默认不回滚 DSH 已执行的任务。
- Discord API 创建成功但本地保存失败、或 Session 创建成功但频道创建失败时，必须有可恢复的中间状态，避免重试制造重复对象。

## 四、必须处理的现有作用范围问题

重新核查以下已发现的行为，并修正新模式下的语义：

1. 当前跨工作区 `/session` 绑定可能修改 Bot 默认 Workspace，并 clearSessions() 清除整个 Bot 的其他会话映射。
2. `/workspace` 具有 Bot 全局作用范围。
3. `/preset` 也可能修改 Bot 全局的新会话默认值。
4. 当前对话专属工作区切换会清除当前 Session 绑定。
5. `/history`、`/batch` 等共享命令存在私聊限定。

新模式要求：

- 当前频道的会话操作只能影响该频道。
- 项目设置只能影响明确指定的项目。
- 全局默认设置必须通过明确的管理入口修改。
- 不能只是给旧命令加一个原生 Slash Command 外壳，继续触发上述全局副作用。
- 历史、会话列表、模型、项目路径等查询也要校验访问范围。
- 保留现有非 Discord 渠道及旧 Discord Thread 模式的行为。

优先扩展现有共享业务接口，并为需要不同作用范围的操作增加明确入口，避免复制整套 Harness 业务逻辑。

## 五、Discord 原生交互

请实际实现可用的 Application Commands、组件回调和必要的 Modal，不做只有外观的占位按钮。

命令名称可以按 Discord 规范组织，至少覆盖：

- 项目创建、绑定、查询。
- 会话创建、打开／绑定、状态、历史、归档和恢复。
- 当前会话模型、思考强度选择。
- 停止任务、补充指令、压缩上下文。
- 连接与插件状态诊断。

提供频道会话信息卡，显示项目、工作目录、模型、运行状态及操作入口。

交互要求：

- 问题支持单选、多选及文字补充，按 DSH 实际问题语义实现。
- 审批提供“批准一次”和“拒绝”，沿用 DSH 的权限与审批机制。
- 操作按钮绑定真实的 Session、Turn 和待处理请求。
- 使用服务端保存的操作状态，核查操作者、Guild、Channel、Session、请求 ID、有效期及是否已消费。
- 重复点击、过期点击、跨频道操作以及已经在其他客户端处理过的请求，都要安全返回实际状态。
- 不把频道名、用户传入的任意文本或按钮参数直接当作有权限的底层命令。

接入方式优先继续使用 Gateway，无需为个人部署增加公网回调服务。

收到交互后及时响应或 defer，满足 Discord 首次响应时限。长任务的状态与输出使用普通 Bot 消息持续维护，不依赖最初 Slash Command 的交互 Token 长期有效。

## 六、消息、文件与双向同步

### 1. 频道消息体验

- 已绑定频道内，授权用户直接发消息即可，无需 @。
- 忽略 Bot／Webhook 自发消息，防止循环。
- 流式更新合并发送，遵循真实限流信息。
- 超长回答正确分段，保留代码块、Unicode 和最终答案完整性。
- 较长报告／日志可附带完整文件。
- 明确区分排队、运行、等待用户、等待审批、完成、中断和失败。
- 过程展示以步骤和工具摘要为主，避免大量重复消息。
- 在任务完成、失败或需要操作时提供明确通知。
- 消息创建与编辑均设置 allowed_mentions，避免模型输出意外触发 @everyone 等通知。

### 2. 文件

- 复用现有附件输入与产物回传机制，保持 Session／Turn 来源与投递路由。
- 授权校验通过后及时保存入站附件，不把会过期的 Discord CDN URL 当作永久存储。
- 上传大小和能力根据实际接口结果处理，超限要清楚反馈。
- 不因模型回答中出现一个本地路径就自动上传文件。
- 区分投递成功、明确失败和结果不确定，避免盲目重试造成重复发送。

### 3. DSH 与 Discord 同步

实现已绑定服务器频道与对应 DSH Session 的同步：

- Discord 输入进入该 Session。
- DSH 网页／客户端在同一 Session 产生的新用户消息、助手结果和运行状态能同步到频道。
- 问题、审批和结果文件按实际可用宿主接口接入，明确交付范围。
- 已从 Discord 发出的消息不能被镜像回来后再次作为新任务提交。
- 保存来源标识、事件位置和投递状态，防止重连重复输出。
- DSH 保存会话和任务的真实状态；Discord 保存入口与展示状态。
- 默认同步绑定后的新事件，历史通过查询按需加载。
- Web 和 Discord 操作同一待审批请求，先成功提交的一端生效。

注意：当前 Session Sync 和来自其他客户端的 Discord 审批同步主要限定私聊。请真正扩展服务器频道路径及操作者归属，不能仅打开设置便宣称已经支持。

## 七、持久化、并发与恢复

持久会话映射不等于持久任务队列，请分别实现。

至少保存：

- 服务器、项目、频道与 Session 映射。
- 已接收消息／交互与 DSH 请求／任务的关联。
- 待处理、已提交、运行中、终态及提交结果不确定的状态。
- 结果投递记录和必要的同步游标。
- 创建、绑定、归档等多步骤操作的恢复信息。

在现有架构上选用合适的持久化方式。单实例部署优先保持简单，避免引入本次不需要的外部数据库、Redis 或独立多租户服务。

恢复规则：

- 重复 Gateway 事件不重复提交已确认接收的任务。
- Discord 断线而 DSH 仍在运行时，恢复后继续跟踪原任务。
- DSH 重启导致任务中断时明确显示中断。
- 请求提交结果不确定时，先关联 DSH 状态与历史核实，不能直接重放可能已执行的命令。
- 队列中的任务在重启后仍可识别和处理；过期或上下文条件改变的任务不能静默执行。
- 不声称未经验证的 exactly-once。

并发规则：

- 同一 Session 的提交与控制保持一致。
- 受管会话的全局重任务并发可配置，默认 1。
- 同项目受管会话默认串行，避免同时修改同一目录。
- 不同项目可以在配置允许时并行。
- 利用 DSH 实际提供的运行状态／协调能力检测其他入口正在运行的任务；无法覆盖的并发范围在文档中明确说明。
- 并发保护要通过程序实现，不能只依赖提示词提醒模型。

Discord API 限流应按响应中的 Bucket、Retry-After／retry_after 等信息调度，不采用忽略平台要求的固定短等待。停止、审批等控制请求不应被大量进度更新长期阻塞。

## 八、归档与容量管理
